# Support copilot workspace

A browser-facing support workspace pairs a LangGraph/OpenAI agent with CopilotKit chat. The agent can inspect synthetic cases and save a refund proposal. A support operator approves or rejects the proposal in the main case view. Only that explicit decision updates the order's refunded amount and the refund ledger. The view polls the backend's committed case state, so the displayed result agrees with the records.

## Run locally

Requires Python 3.12, Node.js 20+, `uv`, npm and an OpenAI API key for chat. In one terminal:

```sh
cp fixtures/starter.json workspace.json
cd backend
uv sync --dev
OPENAI_API_KEY=... uv run support-workspace-api
```

In a second terminal:

```sh
cd frontend
npm ci
npm run dev
```

Open `http://localhost:3000`. The API binds `127.0.0.1:8123`; the Next.js runtime forwards CopilotKit chat to its `/agent` AG-UI endpoint. The frontend fetches case records directly from that local API. Without an OpenAI key the backend fails at startup rather than showing canned agent responses. The self-hosted CopilotKit path does not need an Intelligence project key; optional managed threads and inspector features are outside this example.

`NEXT_PUBLIC_SUPPORT_API_URL` selects the frontend's case API, `SUPPORT_AGENT_URL` selects its server-side AG-UI destination, and `SUPPORT_WEB_ORIGIN` configures the backend's one allowed browser origin (default `http://localhost:3000`). Supply frontend environment values before starting or building Next.js.

Copy the fixture to a new `workspace.json` to reset. One backend process owns the file; the lock is process-local and does not support multiple server workers. The API has no user authentication and is for local demonstration only. No real refund processor or customer mailbox is connected.

## Proposal and approval state

A proposal binds the exact order ID, customer email and currency observed when it was created. Approval rechecks this binding, the current case/order identity, delivery status and remaining captured balance. A changed binding returns 409 and requires a fresh proposal. Older unbound proposals can be rejected; they must be recreated before approval. Exact duplicate proposals preserve the displayed revision rather than invalidating an operator's pending decision. Amounts and revisions must be exact integers; booleans/fractions and unexpected decision fields are rejected.

The local snapshot validates unique case/order/refund IDs, captured/refunded amounts and committed resolution relationships. New refund IDs preserve noncontiguous imported history. Each proposal/decision publishes through a private staged file, flush/fsync and atomic replacement; failed publication leaves the previous file readable and removes the stage. This is local-file consistency under one process, not a cross-process or remote payment guarantee.

## Verification and limits

Run `cd backend && uv run pytest` and `cd frontend && npm run typecheck && npm run build`. Twenty-six backend checks cover proposal-only effects, approval/rejection, stale revisions, ineligible orders, exact integer amounts, changed order/customer/currency bindings, legacy unknown scope, imported refund IDs and failed file publication.

The browser suite runs without a model key:

```sh
cd frontend
npm ci
npx playwright install chromium
npm run test:e2e
```

Keep `uv` on PATH and install the backend dependencies first with `cd backend && uv sync --dev --locked`. The suite starts its own local API on port 38123 and Next.js on port 3300, refuses to reuse an existing listener, resets `frontend/.e2e/workspace.json` for each case, and stops both owned processes afterward. Run one browser suite at a time. The test API deliberately omits `/agent`; proposals are seeded as fictional starting state rather than generated by a model. It uses the real decision endpoint, persisted JSON state, and Chromium UI.

On 2026-10-15, all six browser cases passed: a 2,999-cent refund persisted and remained visible after reload; rejection left payments unchanged; processing-order and stale-revision conflicts stayed visible; a delayed read of a previous case could not replace the selected case; and a USD proposal could not commit after the order changed to CAD. The suite caught a disappearing conflict message before the UI fix. It retains an actual approval screenshot under `frontend/test-results/`, plus traces/screenshots on failure. CI runs the same suite with Playwright `1.64.1` and retains synthetic browser evidence for seven days. Generated workspaces and browser artifacts are ignored by Git.

Nine native checks retain actual LangChain/OpenAI implementations and the real `/agent` AG-UI adapter, replacing only model HTTP with controlled JSON/SSE. They reproduced a `length`-terminated tool call executing a proposal. A [LangChain after-model middleware guard](https://docs.langchain.com/oss/python/langchain/middleware/custom) now blocks nonfinal/refused/invalid/parallel output before tool dispatch, with matching synchronous and asynchronous hooks. The streaming error case emits RUN_ERROR without RUN_FINISHED or a proposal. A completed native loop saves only a proposal, never a refund. Calls are bounded to eight per run, 30-second HTTP timeouts, no automatic retry, 4,096 output tokens and no model cache/storage.

`agent_observations` saves each returned SDK message, acceptance/error reason and conversation thread ID. `sdk_usage` is the SDK's measurement; raw transport-level `reported_usage` and cost remain unknown. Rejected messages stay in this durable evidence, but are removed from later provider context so a new turn has no unanswered tool-call ID. Streamed token/tool fragments can appear before validation; RUN_FINISHED and committed state determine completion.

`scenarios/README.md` distinguishes these SDK/API/browser checks from live model behavior. No paid model call or complete browser chat proof has been made. Owned model/checkpointer lifecycle, raw transport usage/errors and expanded busy/ambiguous/boundary datasets remain development work.
